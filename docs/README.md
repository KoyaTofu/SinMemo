# 書類の案内

- 版: 1.2（2026-11-17 2.0 音声入力の 1.1 事前調査（#1）で、事前調査/ を足し、類似調査を移した。Issue・PR の番号の書き方を足した）。前の版: 1.1（2026-11-17 旧#53 ふりかえりを記録/ に移し、案内に足した）。前の版: 1.0（2026-11-16 公開に向けて組み直し）
- 関連書類: [要件定義書](要件/要件定義書.md)、[スケジュール](記録/スケジュール.md)

SinMemo（シンプルなメモ帳 Android アプリ）の書類の置き場所と読み方をまとめる。書類はすべて日本語の Markdown。

## 1. 開発の流れ

SinMemo は「アプリ開発の一連の流れを学ぶ」ために作った。次の順に進めた（日程と実績は [スケジュール](記録/スケジュール.md)）。

| 順 | 工程 | やったこと | 主な書類 |
|---|---|---|---|
| 1 | 要件 | 似たアプリを調べ、作るもの・作らないものを決めた。画面を決め、モックアップで確かめた | [要件/](要件/)、[モックアップ検証](記録/モックアップ検証.md) |
| 2 | 設計 | 機能ごとに、ユーザーから見える動き（基本設計）と作り方（詳細設計）を決めた | 各機能のフォルダの `基本設計.md`・`詳細設計.md` |
| 3 | 実装 | 設計に沿ってコードを書いた（`app/`） | - |
| 4 | テスト | 機能ごとに、PC の自動テスト・エミュレータ・実機で確かめた | 各機能のフォルダの `テスト設計.md`・`テスト結果.md` |
| 5 | 総合テスト | 実機でシナリオを通しで操作し、性能（起動 2 秒・1,000 件）を測った。見つかった不具合は直した | [総合テスト/](総合テスト/)、[セキュリティ/](セキュリティ/) |
| 6 | リリース | 署名付きのリリース APK を作り、自分の端末に入れた | [リリース/](リリース/) |

- 2〜4 は機能ごとに繰り返した（基盤 → 一覧 → 編集 → 下書き → 設定 → アイコン）。工程ごとに PR を 1 本にした
- 決定・確認・承認は開発者、書類とコードの作成は Claude Code が行った

## 2. 読む順

0. [事前調査/](事前調査/): 要件を決める前に調べた似たアプリ
1. [要件定義書](要件/要件定義書.md): 何を作るか（目的・範囲・機能要件・非機能要件）
2. [機能一覧](要件/機能一覧.md)・[画面一覧](要件/画面一覧.md)・[ユーザーシナリオ](要件/ユーザーシナリオ.md): 機能・画面・使い方の一覧
3. 各機能の基本設計: [共通](共通/基本設計.md) → [メモ一覧](メモ一覧/基本設計.md) → [メモ編集](メモ編集/基本設計.md) → [下書き](下書き/基本設計.md) → [設定](設定/基本設計.md) → [アイコン](アイコン/基本設計.md) → [リリース](リリース/基本設計.md)
4. 作り方を知りたいとき: 各機能の詳細設計
5. 確かめ方と結果: 各機能のテスト設計・テスト結果、[総合テスト](総合テスト/テスト設計.md)、[セキュリティ](セキュリティ/テスト設計.md)
6. 経緯: [スケジュール](記録/スケジュール.md)、[作業メモ](記録/作業メモ.md)、[ふりかえり](記録/ふりかえり.md)

## 4. 書類の種類

| 種類 | ファイル名 | 書くこと | 主に読む人 |
|---|---|---|---|
| 事前調査 | `事前調査/` | 似たアプリ・プロジェクトの調査。要件を決める前の材料 | 開発者（決める人） |
| 要件 | `要件/` の 4 本 | 何を作るか・作らないか。機能・画面・シナリオの一覧と ID | 開発者（決める人）、全員が最初に読む |
| 基本設計 | `基本設計.md` | ユーザーから見えること。画面と操作、操作ごとの動き、メッセージ、決めたこと | 開発者（確かめる人）、テストを考える人 |
| 詳細設計 | `詳細設計.md` | 作り方。クラス・部品の分け方、データの項目、処理の流れ、使うライブラリ。コードは書かない（コードは `app/`） | 実装する人、コードを読む人 |
| テスト設計 | `テスト設計.md` | 何をどう確かめるか。「自動テスト（PC、Robolectric）」「エミュレータ」「実機」に分け、項目に ID を付ける | テストする人、開発者（実機の確認） |
| テスト結果 | `テスト結果.md` | 実施した日・環境・コマンドと出力、ID ごとの結果、見つかった問題と対応、できなかったこと・残り | 開発者（承認する人）、後で振り返る人 |
| 記録 | `記録/` | 日程、作業の経緯や注意 | 後で振り返る人 |

- 各書類の最後に「決定事項」の表がある。途中で変えた決定は「→ こう変えた（理由）」と書いている
- ID の付け方: 機能は `F-01`、要件は `FR-01`、シナリオは `US-01`、画面は `S-01`、ダイアログは `D-01`、画面遷移は `T-01`（いずれも [要件/](要件/)）
- WBS 番号（例: 4.3）は [スケジュール](記録/スケジュール.md) の工程。2.0（音声入力）は別の表で 1 から振り直したので、「2.0 の 1.1」と書く
- Issue・PR の番号: 1.0 の書類にある `#45` などは、開発に使った非公開のリポジトリの番号で、ここからは開けない。2.0 からはこの公開リポジトリの番号を `#1` と書き、古い番号を新しく書くときは `旧#45` と書く

## 5. テスト ID の付け方

テスト設計の項目には `<接頭字>-<場所>-<番号>` の形の ID を付ける。

| 位置 | 意味 | 値 |
|---|---|---|
| 接頭字 | どのフォルダのテストか | フォルダごとに決める。各フォルダの `テスト設計.md` の冒頭を見る |
| 場所 | どこで確かめるか | `U` 自動テスト（PC、Robolectric）／`B` ビルドの確認（PC）／`E` エミュレータ／`D` 実機 |
| 番号 | 通し番号 | `01` から |

例: 接頭字が `L` なら `L-U-01`（自動テストの 1 番）、`L-E-01`（エミュレータの 1 番）、`L-D-01`（実機の 1 番）。テスト結果では、この ID ごとに結果を書く。

セキュリティ・総合テストはこの形でなく、各テスト設計の冒頭の ID の付け方による。

## 6. テストの実行

| 種類 | コマンド | 備考 |
|---|---|---|
| 自動テスト（PC） | `./gradlew testDebugUnitTest` | Robolectric で画面のテストも PC で動く |
| 計装テスト（エミュレータ・実機） | `./gradlew connectedDebugAndroidTest` | 端末をつないで実行 |

詳しい手順と結果は各フォルダのテスト設計・テスト結果を見る。
