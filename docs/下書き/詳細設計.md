## 1. 仕組み（`SavedStateHandle`）

Android には、システムがアプリを終了するときに**画面ごとの小さな状態を保存し、戻ってきたときに返してくれる仕組み**（保存されたインスタンス状態）がある。ViewModel からは `SavedStateHandle` として使える（編集画面が memoId を読むのに使っているもの）。この仕組みで書きかけを持つ（[基本設計](基本設計.md) 決定事項 2）。

- A（画面ごと戻る）では保存した状態が返ってくるので、本文を戻せる
- B（最初から起動）では状態そのものが残らないので、**何もしなくても「一覧を開き、書きかけは残さない」になる**。DB に書かないので、消す処理も要らない
- 1 画面に 1 つなので、書きかけは自然に「1 件だけ」になる

## 2. 書くタイミング

| きっかけ | 動き |
|---|---|
| 編集画面が裏に回った（`ON_STOP`） | 画面（`MemoEditScreen`）が `LifecycleEventEffect(ON_STOP)` で `MemoEditViewModel.onStop()` を呼ぶ。ViewModel は今の本文を `SavedStateHandle` に入れる（キー `draftBody`） |

- Android 9 以降、システムが画面の状態を保存するのは `ON_STOP` の後なので、`ON_STOP` で入れた本文が保存される
- 変更があるかどうかに関係なく入れる
- 次のときは書かない: 読み込み中（本文がまだないので、空の本文で上書きしてしまう）、保存・削除の処理中、閉じた後
- 保存・破棄・削除で編集画面を閉じると、画面の状態ごと捨てられるので、消す処理は要らない
- 画面回転でも `ON_STOP` が起きるが、ViewModel はそのまま残るので影響はない

## 3. 戻すとき（`MemoEditViewModel` を作るとき）

1. `SavedStateHandle` の `draftBody` を読む。なければ今までどおり（[メモ編集 詳細設計](../メモ編集/詳細設計.md) 3 章）。最初から起動したときは画面の状態がないので、必ず「なし」になる
2. あれば（= A で戻ってきた）、状態の `isRestored` を true にする
   - 新規: 元の本文は空のまま、入力欄に `draftBody` を入れる
   - 既存: DB からメモを読んで元の本文にし、入力欄には `draftBody` を入れる
   - 既存だがメモが見つからない: memoId を新規（`NEW_MEMO_ID` = 0）に切り替え、元の本文を空にして入力欄に `draftBody` を入れ、`isNew` を true にする（[基本設計](基本設計.md) 決定事項 3）。⋮ は出ず、✓ で新しいメモとして保存される
3. 画面は「新規で、かつ `isRestored` でない」ときだけ入力欄にフォーカスを当ててキーボードを出す。書きかけを戻したときは出さない

## 4. 大きさ
- 本文は最大 10,000 文字（UTF-16 で約 20KB）。画面の状態として保存できる量（目安で数百 KB まで）に十分収まる

## 5. 部品ごとの変更

| 場所 | 変更 |
|---|---|
| `MemoEditViewModel` | `draftBody` を読む（3 章）。`onStop()` を追加（2 章）。元のメモが見つからないとき新規に切り替える。キー名は定数 `KEY_DRAFT_BODY` |
| `MemoEditScreen` | `LifecycleEventEffect(Lifecycle.Event.ON_STOP)` で `viewModel.onStop()` を呼ぶ。キーボードを自動で出すのは「新規で、かつ `isRestored` でない」ときだけ |
| `MemoEditUiState` | `isRestored`（書きかけを戻して開いた）を追加。`isNew` は「元のメモが見つからず新規に切り替えた」ときも true になる |
| DB・リポジトリ | **変更なし**（下書きの表、DB の版上げ、`DraftRepository` は作らない） |
| NavHost | **変更なし**（起動時に編集画面を自動で開く処理は作らない） |

- メモ編集の設計で「下書きを消す処理は後で追加する」としていた箇所（保存・削除・破棄）は、2 章のとおり処理が要らなくなったので、消した

## 6. 保存・削除を始めたら書きかけを捨てる（7.4。#59 その他。[基本設計](基本設計.md) 4 章）

開発者の決定（2026-11-17）。`MemoEditViewModel` の中の順番は [メモ編集 詳細設計](../メモ編集/詳細設計.md) 9.2・9.4。

| 時 | `SavedStateHandle` への操作 |
|---|---|
| `onSave()` で DB に書くと決めた（`isBusy` = true の直後。DB に書く前） | `remove<String>(KEY_DRAFT_BODY)` と `set(KEY_CLOSED, true)`（キー `closed`） |
| `onDeleteConfirm()`（`isBusy` = true の直後。DB に書く前） | 同じ |
| 保存・削除が成功した | 何もしない（印は付いている）。`close` する |
| 保存・削除が失敗した | `remove<Boolean>(KEY_CLOSED)` と `set(KEY_DRAFT_BODY, 今の本文)` |
| `onStop()` | 今のまま（読み込み中・処理中・閉じた後は書かない） |

ViewModel を作るとき（3 章の前に足す）
1. `savedStateHandle.get<Boolean>(KEY_CLOSED) == true` なら、`MemoEditUiState(isClosed = true)` で始め、読み込みも書きかけの復元もしない（`savedMemo` はなし。一覧の位置は動かさない）
2. そうでなければ 3 章のとおり

- 「終わった」印は、保存が終わってから一覧へ戻るまでの間（アプリが裏にいると、画面が状態を見られないので戻れない）に終了されたときのため。印がないと、戻ったときに新規の編集画面（空）や既存のメモが開き、閉じたはずの画面が出る
- 印を DB に書く**前**に付ける理由: システムが画面の状態を保存するのは裏に回ったとき（`ON_STOP` の後）の 1 回だけ。処理中に裏に回ると、その時点の中身（書きかけなし・印あり）が保存され、そのあとに保存が終わっても保存し直されない。成功したあとに印を付けると、保存された中身に印が入らず、終了から戻ったときに空の新規の編集画面が開く（7.4 の確認役の指摘で直した）
- 割り切り: 処理中に裏に回って状態が保存され、そのあとに**失敗**し、次に裏に回る前に終了された場合は、保存された中身（印あり）で戻るので、一覧へ戻り、書いた本文は失われる。失敗と終了が重なることはまれなため
