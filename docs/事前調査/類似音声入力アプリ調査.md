- 用語:
  - ※用語：文字起こし … 話した声を文字にすること。この書類では「音声認識」と同じ意味で使う
  - ※用語：認識アプリ … 声を聞いて文字にする役のアプリ（例: Google アプリ、FUTO Voice Input）。Android ではほかのアプリから呼び出せる
  - ※用語：IME … 文字を入力するキーボードのアプリ（例: Gboard）
  - ※用語：モデル … 声を文字にするための学習済みのデータ。端末の中で文字にするアプリは、これを端末に入れる（数十〜数百 MB（推測））
  - ※用語：Whisper・Vosk … 端末の中でも動かせる文字起こしの仕組み（OSS）
  - ※用語：オフライン … ネットにつながっていなくても動くこと。「声が端末の外へ出ない」とは同じではない（ネットにつながっていれば送るアプリもありうる）ので、この書類では分けて書く

## 2. 各アプリの整理

### A. FUTO Voice Input（ソース公開）
- 想定ユーザー: Google に声を送らずに音声入力をしたい人。プライバシー重視
- 主なシナリオ: キーボードのマイクを押して話す／ほかのアプリの「音声で入力」ボタンから呼ばれて、画面の中央に浮いた小さな画面で話す
- 主要機能: モデル（Whisper、Parakeet、asr4all）による文字起こし（日本語を含む 17 言語）、声の区切りの検出、キーボードの音声モード、`ACTION_RECOGNIZE_SPEECH` を受ける画面。`SpeechRecognizer` の API には対応していない（README。マニフェストには、`SpeechRecognizer` で有無を調べるアプリのための形だけのサービスがある）
- 起動の形: 認識の画面は浮いた画面で、別のタスクで開く（`launchMode="singleInstance"`）
- 声の扱い: アプリの画面の文言に「Completely offline app」「your data stays on your device」（`strings.xml`）。マニフェストには `INTERNET` があり、更新の確認とモデルの取得に使う（`UpdateCheckingService`・配布元の URL。ソースで確認）。課金の画面もある
- アプリの権限（マニフェスト）: `RECORD_AUDIO`、`INTERNET`、`ACCESS_NETWORK_STATE`、`POST_NOTIFICATIONS`、`RECEIVE_BOOT_COMPLETED`
- 技術構成: Kotlin、ggml 系の推論（transcribe.cpp。whisper.cpp 由来）、minSdk 24、FUTO Source First License 1.0（ソースは読めるが、一般的なオープンソースのライセンスではない）。README に「開発の中心は FUTO Keyboard（音声入力を内蔵）に移った」
- 情報源: https://github.com/futo-org/voice-input

### B. Whisper+（whisperIMEplus、OSS）
- 想定ユーザー: オフラインで音声入力をしたい人
- 主なシナリオ: キーボード（例: HeliBoard）のマイクから呼ぶ／ほかのアプリから `ACTION_RECOGNIZE_SPEECH` で呼ばれる／単体で使う（英語への翻訳もできる）
- 主要機能: Whisper（ONNX）による文字起こし、2 つの言語の切り替え、キーボード・`RecognitionService`（※用語：システム全体の音声認識の受け口）・`ACTION_RECOGNIZE_SPEECH` の 3 つの入口。結果を PendingIntent で返す受け取り方（`EXTRA_RESULTS_PENDINGINTENT`）にも対応
- 起動の形: 浮いた画面（`launchMode="standard"`。2 回呼ばれると 2 つ開きうる）
- 声の扱い: 「最初にモデルをダウンロードしたあとは完全にオフラインで動く」（README）。マニフェストに `INTERNET` はなく、モデルはブラウザで Hugging Face のページを開いて取る（ソースで確認）
- 制限: **1 回の録音は 30 秒まで**（README、ソースの 30 秒のタイマー）
- アプリの権限（マニフェスト）: `RECORD_AUDIO`、`FOREGROUND_SERVICE_MICROPHONE`、`QUERY_ALL_PACKAGES`、Bluetooth 関係ほか
- 技術構成: Java、minSdk 28、GPL-3.0。README に「Google の開発者の身元確認の義務化で、2026/2027 年以降は認定端末で動かなくなる」との注意あり
- 情報源: https://github.com/woheller69/whisperIMEplus

### C. Sayboard（OSS）
- 想定ユーザー: オフラインの音声キーボードがほしい人
- 主なシナリオ: キーボードを Sayboard に切り替えて話す
- 主要機能: Vosk による文字起こし（日本語のモデルあり）、複数の言語、`RecognitionService`（4.2.0 で追加）。`ACTION_RECOGNIZE_SPEECH` は受けない
- 声の扱い: 「Sayboard はあなたの情報をインターネットへ送らない」（README）。`INTERNET` はモデルのダウンロードだけに使い、なくてもよいと書いている
- アプリの権限（マニフェスト）: `RECORD_AUDIO`、`INTERNET`、`FOREGROUND_SERVICE_MICROPHONE` ほか。README には、Android の不具合のため `RecognitionService` を動かすのに `QUERY_ALL_PACKAGES` が要るとある
- 技術構成: Kotlin、minSdk 23、GPL-3.0。最後の更新は 2025-07（取得したリポジトリの最新のコミット）
- 情報源: https://github.com/ElishaAz/Sayboard 、https://f-droid.org/packages/com.elishaazaria.sayboard/

### D. Omni-Notes（OSS、メモ帳）
- 想定ユーザー・シナリオ: 類似メモアプリ調査の D と同じ。メモに録音を添えたいとき
- 主要機能（声）: 編集画面で録音し、音声ファイルとしてメモに添付する（`MediaRecorder` で録音。ソースで確認）。**文字にはしない**
- 声の扱い: 端末の中に音声ファイルとして残す
- アプリの権限: `RECORD_AUDIO`（録音のときに許可を求める）ほか
- 技術構成: 類似メモアプリ調査の D と同じ（Java 中心、GPL-3.0）
- 情報源: https://github.com/federicoiosue/Omni-Notes

### E. NotallyX（OSS、メモ帳）
- 想定ユーザー・シナリオ: 類似メモアプリ調査の C と同じ。メモに録音を添えたいとき
- 主要機能（声）: 録音をメモに添付する（録音用のサービスがある。ソースで確認）。**文字にはしない**
- 声の扱い: 端末の中に音声ファイルとして残す
- アプリの権限: `RECORD_AUDIO`、`FOREGROUND_SERVICE_MICROPHONE` ほか
- 技術構成: 類似メモアプリ調査の C と同じ（Kotlin、GPL-3.0）
- 情報源: https://github.com/Crustack/NotallyX

### F. Gboard の音声入力（市販）
- 想定ユーザー: Gboard を使う人全般。開発者の端末（OPPO CPH2099、Android 11）のキーボードも Gboard
- 主なシナリオ: 文字を入力できる欄でキーボード上の「マイク」を押し、「お話しください」と出たら話す
- 主要機能: どのアプリの入力欄でも使える、言語の切り替え、句読点（一部の言語で不可）。一部の Pixel では「高度な音声入力」
- 声の扱い: 公式ヘルプには送り先の記載がない。一部の Pixel では端末の中で処理する音声入力があると報じられている。それ以外の端末での扱いは確認できなかった（推測: ネットにつながっていれば Google のサーバで処理する）
- 権限: マイクの許可は **Gboard が** 求める（入力先のアプリには要らない）
- 注意: キーボードは 1.0 のときから、入力欄の文（カーソルの前後の本文）を読める。声と一緒に文脈を処理しうる（推測）。1.0 ではこれを前提として受け入れていたが、書類には書いていない（6 章）
- 技術構成: 非公開
- 情報源: https://support.google.com/gboard/answer/2781851?hl=ja 、https://9to5google.com/?p=276388

### G. Google Keep の音声メモ（市販）
- 想定ユーザー: 一般ユーザー。歩きながらなど、さっと残したい人
- 主なシナリオ: 下のマイクを押して話すと、録音と文字の両方が入ったメモができる
- 主要機能: 録音しながら文字にする、録音を再生できる
- 声の扱い: Google アカウントのクラウドに同期される（Keep 自体がクラウド保存）。文字にする処理の場所は確認できなかった（推測: Google のサーバ）
- 技術構成: 非公開
- 情報源: https://www.popsci.com/diy/how-to-transcribe-voice-memos-into-text 、https://www.alphr.com/google-keep-voice-to-text/ （公式ヘルプのページは見つからなかった）

### H. Pixel のレコーダー（プリインストール）
- 想定ユーザー: 会議・講義を録音して文字で見返したい Pixel のユーザー
- 主なシナリオ: 録音を始めると、その場で文字が出る。あとで文字から検索・書き出し
- 声の扱い: 発表時（2019 年）に「処理はすべて端末の中、ネットなしでも動く」と説明された。今の版での扱いは確認していない
- 制限: Pixel だけ。言語は機種による
- 技術構成: 非公開
- 情報源: https://support.google.com/pixelphone?p=recorder 、https://techcrunch.com/2019/10/15/googles-new-voice-recorder-app-transcribes-in-real-time-even-when-offline/

### I. Samsung のボイスレコーダー・Samsung Notes（プリインストール）
- 想定ユーザー: Galaxy のユーザー
- 主なシナリオ: ボイスレコーダーで録音したものを文字にし、Samsung Notes に送って編集する
- 声の扱い: Galaxy AI の機能。端末の中だけで処理するかは確認できなかった（推測: 設定で選べる）
- 制限: 対応機種は Galaxy S24 以降・Z Fold6／Flip6 などの一部（情報源 2 つ目）
- 技術構成: 非公開
- 情報源: https://www.samsung.com/uk/support/mobile-devices/how-to-use-galaxy-ai-transcript-assist/ 、https://www.samsung.com/ae/support/mobile-devices/how-to-use-text-conversion-of-voice-recording-files-in-notes-on-the-galaxy-z-fold6-flip6/

### J. CLOVA Note（市販のクラウドサービス）
- 想定ユーザー: 会議の記録を残したい人
- 主なシナリオ: 会議を録音し、終わったらクラウドへ上げて文字にしてもらう
- 声の扱い: 録音をクラウドへアップロードし、まとめて文字にする。データの扱いは利用規約・設定による
- その他: 提供の形が変わった（LINE WORKS AiNote へ移行と、競合のブログの記事にある。公式の発表は確認していない）
- 技術構成: 非公開
- 情報源: https://www.itmedia.co.jp/pcuser/spv/2208/02/news091.html 、https://www.notta.ai/blog/clova-note

### K. Kõnele（OSS）
- 想定ユーザー: 標準の音声入力の画面を、Google 以外の認識の仕組みで使いたい人
- 主要機能: ほかのアプリに `ACTION_RECOGNIZE_SPEECH` の画面を提供する。中で使う認識の仕組みは選べる（既定は別アプリのサーバ型。端末の中の仕組みにもつなげる）
- 声の扱い: つなぐ先しだい（既定はオフラインではない（推測））
- 情報源: https://github.com/Kaljurand/K6nele

### L. Transcribro（OSS）
- 想定ユーザー: 端末の中だけで文字にしたい人
- 主要機能: whisper.cpp による文字起こし、キーボードと認識サービス
- 制限: 日本語に対応しているかは確認できなかった（英語だけとする紹介がある）
- 情報源: https://github.com/soupslurpr/Transcribro 、https://alternativeto.net/software/transcribro/about/

## 4. 共通点と相違点

### 共通点
- **録音は「録音の権限を持ったアプリ」がする**。メモ帳が自分で録音するもの（D・E・G）と、ほかのアプリに任せるもの（A・B・F。メモ帳では前回の Markor）に分かれる。任せる形なら、メモ帳には録音の権限が要らない
- **短く話して文字にする使い方と、長く録音してあとで文字にする使い方の 2 つがある**。キーボード・認識アプリ（A〜C・F・K・L）は前者、レコーダー・クラウド（H〜J）は後者
- **プライバシーを売りにするものは「端末の中で文字にする」**（A〜C・H・L）。そのためにモデルを端末に入れる。ただし、ネットの権限まで持たないのは B だけで、A・C はモデルの取得などにネットを使う

### 相違点
- **声の行き先**: 端末の中だけ（A〜C・H・L）／クラウド（J、推測で F・G）。同じ Gboard でも端末・設定で変わる
- **残すもの**: 文字だけ（A〜C・F）／録音と文字（G〜J）／録音だけ（D・E）
- **入口**: キーボード（どのアプリでも使える）／ほかのアプリから呼ぶ画面（`ACTION_RECOGNIZE_SPEECH`）／アプリの中のマイクのボタン
- **呼ばれたときの画面**: 浮いた画面（A・B）。この場合、呼んだアプリは裏に回りきらないことがある（7.3）

### 6.2 プライバシーの評価

- 1.0 の約束は「SinMemo はメモを外へ送らない（権限がないので送れない）」。M-1 でも SinMemo のプログラムが送らないことは変わらない
- しかし、声は**これから書くメモの本文そのもの**で、M-1 では SinMemo の「マイク」ボタンが入口になる。ユーザーは README と権限を見て「声も外へ出ない」と受け取りうる。権限の要件は形の上では守れても、約束の中身は弱まる
- 一方、キーボード（IME）は 1.0 のときから本文を読める立場にあり、Gboard の音声入力（M-5）も同じく声を処理する。1.0 はキーボードを信用する前提を置いていたが、書類には書いていない。M-1 と M-5 は、「SinMemo が入口を用意するか」が違うだけで、声の行き先の問題は同じ物差しで比べるべき
- 守り方の候補（組み合わせられる）: ①書類（README・要件・セキュリティ）に書く ②初めてマイクを押したときに「声は認識アプリが処理し、ネットへ送ることがある」と知らせる ③設定でマイクのボタンを消せる ④`EXTRA_PREFER_OFFLINE` を付ける（効かない認識アプリがあり、オフラインの言語データがないと失敗しうる） ⑤オフラインの認識アプリ（B など）を使い方として案内する。どれを選ぶかは 9 章 論点 2

## 7. 本文の上限・結果の受け取り・画面の行き来・キーボードとの関係

### 7.1 本文の上限 10,000 文字

今の決まり（[メモ編集 基本設計](../メモ編集/基本設計.md) 3.4・5.3、[詳細設計](../メモ編集/詳細設計.md) 9.6）: 変更後が上限を超え、**かつ増える**変更だけ丸ごと取り消す。2 文字以上増えるはずだったときだけメッセージ。数え方は UTF-16（絵文字は 2 以上）。

- **M-1〜M-4 で結果を入れるのはプログラムからの書き込みで、今の上限の仕組み（`InputTransformation`）を通らない**。同じ判断を、結果を入れるところでも行う必要がある。M-5（キーボード）は入力として入るので、今の仕組みが効く
- 決めること・確かめること:

| 場合 | 例 | 今の決まりに揃えると |
|---|---|---|
| 入れると上限を超える | 9,990 文字に 30 文字の結果 | 丸ごと取り消す（9 章 論点 4） |
| すでに 10,000 文字を超えている本文（5.3） | 10,250 文字に 1 文字の結果 | 増えるので取り消す |
| 選択範囲を置き換え、差し引きで減る・同じ | 20 文字を選んで 5 文字の結果 | 増えないので入る |
| 1 文字の結果で超える | 9,999 文字に「あ」と 1 文字 | 今は 1 文字ならメッセージを出さない。声は「打つたびに出てうるさい」場面ではないので、1 文字でも知らせるか（9 章 論点 4） |
| 絵文字・サロゲート | 9,999 文字に絵文字 1 つ | UTF-16 で数え、2 増えるので取り消す |

### 7.2 返ってくる結果の異常系（悪意のある・不具合のある認識アプリ）

| 場合 | 起きうること | 必要な決まり（案） |
|---|---|---|
| 結果が null、候補のリストが null・空、先頭が空の文字列、成功なのに中身がない | 落ちる、空のまま「変更あり」になる | 何もしない（本文を変えない）。知らせるかは論点 |

### 7.3 画面の行き来・中断・下書きとの重なり

[下書き 基本設計](../下書き/基本設計.md)・[詳細設計](../下書き/詳細設計.md) の今の作り: 画面が裏に回ったとき（`ON_STOP`）に本文だけを残し、戻すときは本文を入れてカーソルを末尾に置く。既存のメモは DB から読み直し、読み込み中は入力欄を出さない。

| 認識の画面が浮いた画面（A・B。Google も同じ形の可能性（推測）） | SinMemo は一時停止（`ON_PAUSE`）だけで裏に回りきらず（`ON_STOP` が来ず）、書きかけが残らないことがある | 「認識の画面の形 × 書きかけを残す時」を実機（Google アプリ）で確かめる（8 章） |
| 認識の画面を開いている間に、システムが SinMemo を終了し、そのあとユーザーが戻る | 書きかけの復元（既存は DB の読み直しのあと）と、結果の受け取りが重なる。結果を先に入れると、あとの復元で上書きされて消える | **結果は、読み込みと書きかけの復元が終わってから入れる**（それまで預かる） |
| 書きかけから戻したとき | カーソルは末尾になる（今の作り）。「カーソルの位置に入れる」（9 章 論点 5）が成り立たない | カーソルの位置も残すか、そのときは末尾に入れるかを決める |
| 回転 | 受け取る仕組みが作り直しのあとに同じ形で登録されていないと、結果が届かない | 設計で決め、回転・「アクティビティを保持しない」で確かめる |
| 認識の画面を開いたまま SinMemo に戻る（A は別のタスクなので、最近使ったアプリから戻れる）。そのあと編集・保存・別のメモを開く・← で一覧へ | 遅れて届いた結果が、別のメモ・保存したあとの画面に入る、または黙って消える | どのメモ向けの結果かを覚えておき、合わなければ捨てる（知らせるかは論点） |
| 保存・削除を始めたあと（下書き 4 章の印あり）に結果が届く | 一覧へ戻る途中 | 捨てる |

### 7.4 偽の認識アプリ

- `ACTION_RECOGNIZE_SPEECH` は、どのアプリでも「受けられる」と宣言できる。正規の認識アプリがない・無効なら、選ぶ画面も出ずに偽のアプリがそのまま開く。ユーザーが「常にこのアプリ」を選べば、その後も開く
- 見た目は SinMemo の機能なので、ユーザーは偽の画面を SinMemo の一部だと思い込みうる。偽のアプリは声を録れ、好きな文字を返せる（返る文字は 7.2 で扱う）
- 必要な決まり（案）: 渡す値に本文・メモの情報を入れない（テストで、出ていく値を調べる）。開く前に開くアプリの名前を出す案（`<queries>` が要る）と、受け入れて書く案は 9 章 論点 11

### 7.5 キーボード・かな漢字変換

| 場合 | 今の決まり | 気を付けること |

| かな漢字変換の途中（未確定の文字）でマイクを押す | 上限で取り消すと、変換中の文字はひらがなのまま確定される（受け入れ済み。[総合テスト テスト結果](../総合テスト/テスト結果.md) 6.6 の E-D-06） | ふつうは画面が移るときに未確定の文字が確定される（推測。IME しだい）。上限ぎりぎりでは、確定と結果の挿入の順で E-D-06 と同じことが起きうる。「変換中にマイクを押し、認識の画面から戻り、結果が入る」組み合わせを、基本設計の表と実機の確認に入れる |

### 7.6 押せる状態・二度押し・元に戻す

| 場合 | 決めること |
|---|---|
| マイクの二度押し（B は 2 回呼ばれると 2 つ開く） | 認識の画面を開いている間はマイクを受け付けない |
| 読み込み中、保存・削除の処理中、D-01・D-02 を出している間 | マイクを押せない（今の「保存中は ✓・←・削除を受け付けない」と揃える） |
| 認識の結果を入れたあと | 「変更あり」になり、← で破棄確認が出る（今の決まりのまま） |
| 長い誤認識を入れてしまった | 元に戻す操作はない（1.0 にもない）。手で消すか、破棄確認でまとめて捨てる。対象外とするなら明記する（10 章） |

## 8. 端末での確認の制約

| 制約 | 影響 | 対応の案 |
|---|---|---|
| クラウドにはエミュレータも実機もない | 本物の認識アプリでの確認はクラウドでできない | M-1 は「認識アプリから返ってくる結果」を差し替えて、PC（Robolectric）で画面のテストができる（推測。詳細設計で決める）。ただし、確かめられるのは差し替えた結果の入れ方まで。7.3 の画面の行き来・7.5 の変換は、多くが実機でしか確かめられない |
| 開発者の端末は adb のタップを受け付けない | 画面の操作は開発者が手で行う | 実機の確認表を短い手順にまとめ、開発者の手が要る確認をまとめて予定に入れる（[ふりかえり](../記録/ふりかえり.md) P-2） |
| 開発者の端末は Android 11 | M-3 は使えない。Android 12 以降の動きは確かめられない | 受け入れる（[ふりかえり](../記録/ふりかえり.md) P-4 と同じ） |
| 開発者の端末で何が開くか分からない（OPPO の最初から入っているアプリ、Google アプリ） | M-1 で何が開くか、画面の形（浮いた画面か）、`ON_STOP` が来るか | 要件定義の前か基本設計の前に、開発者が実機で確かめる: 「マイク」に当たる操作で開く画面、機内モードで文字になるか |
| 機内モードで動いても | 「端末の中で文字にできる」までしか分からない。ネットにつないだときに送らないことまでは分からない | 言い方を「機内モードで動く」にとどめる |
| 声は人・場所によって違う | 認識の正確さは SinMemo では決められない | 正確さは要件にしない（認識アプリの責任）案。確かめるのは「結果が正しく入るか」 |

## 10. SinMemo で最低限必要な機能（候補）

9 章のおすすめのとおりに決めた場合の候補。

| 区分 | 機能 | 根拠 |
|---|---|---|
| 必須（候補） | 編集画面のマイクのボタンで認識アプリを呼び、返ってきた文字を本文に入れる | FUTO（A）・Whisper+（B）・Kõnele（K）が提供する入口（`ACTION_RECOGNIZE_SPEECH`）。SinMemo に権限が要らない |
| 必須（候補） | 初めてマイクを押したときに、声は認識アプリが処理し、ネットへ送ることがあると知らせる | 6.2、論点 2 |
| 必須（候補） | 上限・画面の行き来・下書き・キーボードと組み合わせても、本文と結果を黙って失わず、落ちない | 7.1・7.3・7.5 |
| 必須（候補） | 認識アプリがない・聞き取れない・取り消した・おかしな結果が返ったときに落ちない | 7.2 |
| 対象外（候補） | 録音を残す、録音から文字にし直す | G〜J の機能。要件の対象外「音声などの添付」 |
| 対象外（候補） | 長時間の文字起こし（会議の録音など） | H〜J の使い方。メモ帳の「さっと書く」と違う |
| 対象外（候補） | 認識の仕組みを SinMemo に入れる、クラウドのサービスに送る | M-4・M-6。手間と要件の衝突 |
| 対象外（候補） | 認識の正確さ、言語の選択 | 認識アプリの責任。言語は端末の設定に任せる |
| 対象外（候補） | 入れた結果を元に戻す操作 | 1.0 にもない。破棄確認でまとめて捨てられる |

## 11. 決定（論点 1・2）で変わること

決定事項 1・2 のとおり M-2（`SpeechRecognizer`）＋オフラインの指定にした場合に、調査の 5〜7 章から変わること。要件定義でこれを前提に書く。

| 項目 | 変わること |
|---|---|
| 権限（[要件定義書](../要件/要件定義書.md) 5 非機能） | SinMemo が `RECORD_AUDIO` を持つ。「不要な権限を要求しない」を「音声入力のための録音の権限だけは求める。インターネットの権限は持たない」に書き直す。マニフェストに `<queries>`（`RecognitionService`）も足す |
| 権限を求める画面 | 初めて「マイク」を押したときに、Android の許可の画面が出る。Android 11 では「アプリの使用中のみ許可」「今回のみ」「許可しない」を選べる。決めること: 許可しなかったとき、2 回断って二度と聞かれなくなったとき（設定から許可してもらう案内）、「今回のみ」のあと、しばらく使わないと許可が自動で外れたとき（Android 11 の仕組み）、使っている途中で設定から許可を外したとき |
| 声の行き先（6.2） | 文字にするのは端末の既定の認識サービス（ふつうは Google（推測））。オフラインの指定は「実装によっては効かない」ので、**SinMemo からは、声が外へ出ないことを保証できない**。効くかどうかは 12 章で確かめ、要件の書き方（「オフラインを頼む」か「オフラインでしか動かさない」か）を決める |
| オフラインの言語データ | 日本語のオフラインのデータが端末に入っていないと、オフラインの指定では失敗しうる（推測）。そのときの知らせ方（「オフラインの音声データがありません」など）を決める。言語データが入っていないことを知る仕組み（`ERROR_LANGUAGE_UNAVAILABLE` など）は Android 12 以降なので、Android 11 ではほかの失敗と区別できないかもしれない（推測） |
| 画面 | 聞き取り中の表示（聞いている・止める）を SinMemo が作る。M-1 と違い、画面は移らない |
| 7.3 画面の行き来・下書き | 認識アプリの画面へ移らないので、「浮いた画面で `ON_STOP` が来ない」「戻ったときの結果の受け取り」は起きない。代わりに、**聞き取り中に裏に回った・回転した・保存や ← を押したときに、認識を止めるか・途中の結果をどうするか**を決める（[SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer) は使い終わったら必ず片付ける（`destroy`）決まりがある） |
| 7.4 偽の認識アプリ | 呼び先は端末の設定で選ばれた既定の認識サービスなので、「呼ぶたびに偽のアプリが開く」形の横取りはない（推測）。返ってくる結果は今までどおり信用しない（7.2） |
| 7.1 上限 | 変わらない（結果はプログラムから入れるので、今の上限の仕組みを通らない） |
| 確かめ方 | 認識サービスを差し替えて PC でテストできるかは、詳細設計で調べる（推測: 認識の部分を包んで差し替える）。本物の声・オフラインの動きは開発者の実機 |

## 12. 要件定義の前の実機での確認（開発者）

決定事項 4 のとおり、要件定義の前に、開発者の端末（OPPO CPH2099、Android 11）で次を確かめる。adb のコマンドは画面のタップを使わないので、開発者の端末でも動くはず（推測）。結果は「見ること」の列の右に書き足すか、PR のコメントで知らせてもらう。

| No | 開発者の操作 | 見ること・書き留めること |
|---|---|---|
| R-1 | PC で `adb shell settings get secure voice_recognition_service` を実行する | 端末の既定の認識サービスの名前（例: `com.google.android.googlequicksearchbox/...`）。何も出ない・`null` ならそのことを書く |
| R-2 | PC で `adb shell cmd package query-services -a android.speech.RecognitionService` を実行する | 認識サービスを持つアプリの一覧（OPPO のアプリがあるか）。エラーになったら飛ばしてよい |
| R-3 | 端末の「設定」で「デフォルトのアプリ」（または「アプリ」）を開き、「音声入力」や「アシストと音声入力」の項目を探す | 選ばれている音声入力のアプリの名前。項目がなければそのことを書く（場所は機種で違う） |
| R-4 | 「Google」アプリの設定を開き、「音声」の中の「オフライン音声認識」（またはそれに近い項目）を探す | 日本語のオフラインのデータが入っているか（「インストール済み」など）。項目が見つからなければそのことを書く（場所は推測） |
| R-5 | 端末を機内モード（Wi-Fi も切る）にし、SinMemo の編集画面で Gboard のマイクを押して日本語で話す | 文字になるか、エラーが出るか。※Gboard とアプリの中の認識（M-2）は使う仕組みが違うことがあるので、参考として見る |
| R-6 | 機内モードを戻す | − |

- R-1〜R-4 で、M-2 で使われる認識サービスと、オフラインの日本語のデータの有無が分かる。オフラインの指定が本当に効くか（ネットにつながっていても送らないか）は、アプリができてからでないと確かめられない（8 章）
- 確かめた結果で、要件の「オフライン」の書き方（論点 2 の決定をどう要件にするか）を決める
