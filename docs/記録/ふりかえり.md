## 5. 次回: 複数のエージェントで役割を分けるときの進め方（決定事項 1〜5）

### 5.1 役割
開発者と、エージェントの 4 役で進める。

| 役 | 担当すること | 担当しないこと |
|---|---|---|
| **開発者**（決める人） | 進行役から取り次がれた質問に答える。要件と基本設計を読んで承認する。PR のマージ。実機での**振る舞いの確認** | ソースコードのレビュー |
| **進行役**（統括） | WBS・Issue・PR の管理。各役への依頼と、役どうしの受け渡し。**開発者への質問の取り次ぎ**（各役の質問を、原文から変えすぎずにまとめて開発者に渡し、答えを質問した役に返す）。マージの順番と、開発者に見てほしいところの案内 | 設計・コード・レビューそのもの。質問の中身を言い換えて意味を変えること |
| **設計役** | **要件（ユーザーシナリオを含む）、基本設計、詳細設計、テスト設計**の書類（`docs/`）。決めることがあれば選択肢とおすすめを付けて進行役に渡す | ソースコード（設計書にも書かない） |
| **実装役** | **ソースコード**（アプリのコードと自動テストのコード）、**モックアップ**（基本設計の画面を触れる形にしたもの）、**実行環境の整備**（ビルド・SDK・CI・エミュレータ）。ビルドとテストを流して結果を記録する | 設計を勝手に変える（変えたいときは進行役を通して設計役に戻す） |
| **確認役** | 設計役の書類を元に、実装役の作業をレビューする（設計どおりか、テスト設計の項目がすべてテストになっているか、わざと壊すとテストが失敗するか、秘密情報が入っていないか）。指摘を PR に書く | 自分で直す（直すのは実装役）。設計書のない判断 |

- 自動テストのコードは実装役が書き、確認役がテスト設計と照らし合わせる（決定事項 2）
- **攻撃役**（隠れ役割。決定事項 7）: 実務の 3 役（設計役・実装役・確認役）の成果にダメ出しをし、欠陥を指摘する。進行役が成果ごとに呼び、指摘は進行役を通して担当の役に戻す（攻撃役は自分で直さない）。見るのは、設計の抜け・矛盾、異常系の考え漏れ、実装の不具合・弱点（セキュリティを含む）、確認役の見落とし。開発者の決定そのものは対象にしない

### 5.2 開発者が見るもの（決定事項 3）
| もの | 開発者がすること |
|---|---|
| 要件・基本設計の PR | 読んで承認し、マージする |
| 詳細設計・テスト設計・ソースの PR | **中身は読まない**。確認役の OK と自動テストの合格を見てマージする |
| アプリ | 工程の区切りで、実機で振る舞いを確かめる（進行役が確認表を用意する） |

### 5.3 設計書の書き方（決定事項 4）
- ~~機能ごとの設計書は 1 つのまま、中を章ではっきり分ける~~ → **要件・基本設計・詳細設計・テスト設計を別々の書類にする**（テスト設計は自動テスト・エミュレータ・実機と量が多くなるため）

| 書類 | 書くこと | 主に読む人 | PR |
|---|---|---|---|
| 要件 | 何のために何を作るか: 目的、ユーザーシナリオ、機能、非機能（性能・セキュリティなど）、作らないこと。今回の [要件/](../要件/) の書類にあたる | 開発者、全役 | 開発者が読んでマージ |
| 基本設計 | ユーザーから見えること: 画面と操作、振る舞い、状態の組み合わせ（キーボードの有無 × 戻り方 など。K-1）、メッセージ | 開発者、確認役 | 開発者が読んでマージ |
| 詳細設計 | 作り方: 部品の分け方、データの形、処理の流れ（表や図で） | 実装役、確認役 | 確認役の OK でマージ |
| テスト設計 | 何をどう確かめるか。**自動テスト（コード）・エミュレータ・実機**の章に分ける。**正常系だけでなく異常系も**考える（入力の誤り・上限、中断・回転、二度押し、壊れたデータ、権限、攻撃など。決定事項 8）。実機の章は開発者が使う確認表 | 実装役、確認役、開発者（実機の章） | 確認役の OK でマージ |

- **ソースコードは書かない**（関数の中身・コードの断片を書かない。部品や関数の名前を表に書くのはよい）
- 基本設計・詳細設計・テスト設計は機能ごとに作る（例: 「メモ編集 基本設計」「メモ編集 詳細設計」「メモ編集 テスト設計」）。書類どうしは番号で参照する（例: テスト設計の項目から基本設計の振る舞いの番号を指す）
- **モックアップ**（決定事項 6）: 基本設計の画面と振る舞いを元に実装役が作り、確認役が基本設計と照らし合わせる。開発者は触って振る舞いを確かめ、気づいたことは基本設計に戻す（今回の [モックアップ検証](モックアップ検証.md) と同じ使い方）。検証のスクリプトも実装役
- 決定事項の表は、決めたことに近い書類に置く（振る舞いの決定は基本設計、作り方の決定は詳細設計）

### 5.4 1 つの機能の流れ

```
開発者 ◀──質問・答え──▶ 進行役 ◀── 各役の質問
                        │ 依頼
                        ▼
設計役: 要件・基本設計 ──PR──▶ 確認役 ──▶ 開発者が読んでマージ
        詳細設計・テスト設計 ──PR──▶ 確認役 ──▶ 開発者は確認役の OK を見てマージ
                        │
                        ▼
実装役: ソース・テストのコード ──PR──▶ 確認役 ──▶ 開発者は確認役の OK と自動テストの合格を見てマージ
                        │
                        ▼
開発者: 実機で振る舞いを確認（テスト設計の確認表）
```

### 5.5 決まりごと
| No | 決まり | 理由 |
|---|---|---|
| 1 | **1 Issue = 1 エージェント = 1 ブランチ = 1 PR** | ほかの役の作業とぶつからないように。別々の作業フォルダ（git worktree）を使う |
| 2 | **触るファイルを Issue に書く**（担当範囲）。範囲の外を直したくなったら進行役に戻す | 同じファイルの取り合いを防ぐ |
| 3 | **開発者への質問は進行役が取り次ぐ**。選択肢・おすすめ付きは今と同じ。原文から変えすぎない | 開発者が何人ものエージェントから別々に聞かれないように。意味が変わらないように |
| 4 | **受け渡しは Issue と `docs/` だけ**で行う | エージェントはそれぞれ白紙から始まり、会話は引き継がれないため |
| 5 | Issue には「目的・読む書類・やること・やらないこと・完了の条件・触るファイル」を書く（Issue テンプレート） | 4 のため |
| 6 | PR には、確認役のレビューの結果と、開発者に見てほしいところ（あれば 3 つ以内）を書く | 開発者のレビューの負担を減らす |
| 7 | PR ごとに GitHub Actions でテストを流し、通っていない PR はマージしない | 開発者がソースを読まない代わりの守り（K-8） |
| 8 | 共通の決まりは `CLAUDE.md` に集める（報告の形、`--rerun`、テスト件数の数え方、危ない git 操作の禁止など） | どの役も最初に読むので |

**開発者**:
- 4 役（進行役・設計役・実装役・確認役）で進める。役割は 5.1 のとおり
- 書類は 1 つにまとめず、要件・基本設計・詳細設計・テスト設計で分ける（テスト設計はコード・エミュレータ・実機と量が多くなるため）
